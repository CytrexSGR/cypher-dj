# ADR 036: Nested groups in the production mixer

Status: built on the branch `nested-groups` (plan 2026-11-12, tasks 1 to 8) and merged into main on 2026-11-12. Andreas' listening acceptance is open: "build a drum group the Landry way (KICK, PERC, HATS under DRUMS, a saturation chain on DRUMS): does it sound and feel right to work with?"
Decided: by Cypher as defaults in the plan `docs/superpowers/plans/2026-11-12-nested-groups.md` (decisions 1 to 7, following common DAW behaviour) and during the build (decisions 8 to 12 below); Andreas may override. Origin: Andreas, 2026-11-12.
Supersedes: ADR 033 decision 1, the part "depth 1 (groups do not nest)", and the limit of eight groups.
Predecessors: ADR 033 (routing, production master, delay compensation), ADR 035 (host stages as inserts; they sit in group chains too).
Interface text: `docs/architecture/INTERFACES.md` sections 1.5, 4.11 and 20.11.

## Context

The production method "low end first" (the Landry way: skill `cypher-dj-produktion`, folder `landry/`) processes drums in layers: kick, percussion and hats each get their own saturation, EQ and compression, then the whole drum bus gets its own chain and fader. That needs a group inside a group. ADR 033 chose depth 1 as a technical simplification ("decided by me", spec 1.10): the mixer ran tracks, then groups, then the production master in a fixed order, and a group could only play into the master. Eight groups were enough for flat grouping and not for a tree.

The mixer evaluates the groups in one pass. A group that feeds a group needs an order (children before parents), a place to add its output (its parent's sum), a rule for sidechain keys between groups (a key needs a source that has already been computed), a model for delay compensation (a latency stage in a child group delays only the paths through it), and every server function that walks "the group of a track" (loudness, bounce, merge, stems, resample) has to walk the chain.

## Decision

1. **Solo.** Solo on X lets X, all its descendants and all its ancestors play; siblings and their descendants are silent. Mute acts downwards: muting DRUMS silences everything below it, sends included. Mute wins over solo, as before (ADR 033 F2, P7). Reason: it generalises the old rule, and ancestors must play or the soloed signal never reaches the master.
2. **A parent's fader and pan do not act on its children's sends.** Only the mute/solo blend of every ancestor scales them (ADR 033 point 10, extended). Reason: a post-fader send is taken at the child's own fader in every common DAW.
3. **Deleting a group** moves its tracks and child groups to the deleted group's own target (its parent group or the master). Reason: it keeps the sound path; the old "members go to master" is the case of a top-level group. A sidechain key that points at the deleted group is removed with it.
4. **Changing a group's target** blends over `ARR_ZIEL_BLENDE` (480 samples) like a track only when the old target's level in the NEW order is higher than the group's level, so that the old target is still open when the group adds. Otherwise it switches hard at the block start. Reason: groups are processed in the new order; an old target on the same or a lower level has already run, so a blend into it would lose the tail, and A in B turning into B in A would hold a cycle. A hard switch costs at most one block of discontinuity, and only in these moves. A group that plays for the first time blends in from the master to its parent over the same 480 samples, as a track does (a click at most in the first block).
5. **16 groups, depth limited only by the count.** No depth lock in the tools (no locks in Andreas' tools without his yes). `static_assert(ARR_KETTEN <= 64)` because the strip mask has 64 bits. Insert stages per strip (4) and the pools stay; raising them is a separate decision after the cost run of task 9. The strip indexes move: tracks 0..31, groups 32..47, production master 48, returns 49..52. The stellwerk table keeps its first 1258 hashed rows: `grp/9..16` are appended at the table end (`GRP_REGLER_GRUPPEN_NEU`).
6. **Sidechain keys between groups.** A source that is an ancestor of the consumer is `sidechain_zyklus` (pre and post). Otherwise pre is allowed iff level(source) <= level(consumer); post is allowed iff level(source) < level(consumer), else `sidechain_spaet`. With one level this is exactly the old `grp x grp` cell (pre `ja`, post `spaet`), so stored flat projects load as before. The rule "a member does not key its own group" extends to every ancestor. The rule lives in the core (`arr_key.h` `arr_schluessel_urteil`) and in `djk/ui/project/routing_verdict.ts` (`routing_rules.ts` applies it). The level-dependent part is a structural check next to the table, not a new cell: `docs/interfaces/schluessel_regeln.json` and its generated tables (`generate_key.py`, `key_table.ts`) still say only what one level allows (the contract file has no level rule; this ADR is where it is stated).
7. **Balance law** per group unchanged (centre 0 dB), so stacking groups changes no level.

Decisions taken while building:

8. **A command that would break a sidechain key is refused, not repaired.** `ziel_setzen` and `gruppenspur_loeschen` change the levels and the ancestors; if a key of any stage is then a cycle or too late, the whole command is refused with `sidechain_zyklus` or `sidechain_spaet` and the text names the stage. Nothing is removed silently; the user releases the key first. Reason: no silent changes, and undo stays one simple step. It costs convenience. The one exception is the key on a group that is deleted: it goes with the group.
9. **Stems of a grouped source nest under its group.** The group "Stems: <name>" is created with the four to six stem tracks and then plays into the source track's own group (a source on the master gives a group on the master, as before). Reason: the whole chain above the source keeps applying to the stems, the same sound path as decision 3. It affects only new stems runs. With all 16 groups used the stems stay ungrouped, `hinweis: "stems_ohne_gruppe"`.
10. **Group bounce with child groups.** The loudness, bounce, merge and resample renders follow the group chain of the track. A group bounce (`proj_bounce` with `gruppe_id`, or a merge below a group) takes the tracks of the group and of its child groups; a child group between the sources and the bounced group that carries inserts or sends is refused with `merge_inserts` or `merge_sends`, because the dry single-strip render does not bake them in. Remove them or bounce the child group first.
11. **Delay compensation model** (header of `arr_pdc.h`). Arrival is computed per group: `ein(g)` is the arrival of the group's sum before its chain, `aus(g) = ein(g) + latency of its chain`; a child's output is delayed to arrive at `ein(parent)`, a top-level group to `T_G`. Sends of a group have ONE delay place per group (not per group and return): it delays the pre signal of the group, so the return input waits for the latest source. Limits: the send level, the pre/post choice, the fader, the balance and the ancestor blend are applied after that ring, so automation of those on the sends of a child group under latency runs early by up to the delay of the place; static settings are exact. The tail in the send ring is dropped when a group becomes unused. The model assumes every track and every used group may feed every existing return, so it can be more than the longest real path, never less. With one level and no latency stage nothing is delayed and the output is bit-equal to the build before this ADR.
12. **Bit-identity without nesting** is the acceptance rule of the build: `kGolden = 0xb8fafa36680592e3` and the stellwerk hash over the first 1258 rows stay; a project without nesting is saved byte for byte as before (`Gruppe.ausgang` is not written when it is the master) and its playback file is the same `/1` or `/2` as before.

## Consequences

- **Formats.** The project file gets an optional `ausgang` on a group (`{art: "gruppe", id}`; absent = master). The playback file lets a group's `ausgang` have the `art` `gruppe` with `nr`; a cycle, a self reference or a parent that is not in `gruppen` is `format`. `grp/<n>/*` and the send paths run to n = 16. Old cores refuse a playback with a nested group; core and render program must be built and started together.
- **Two places refuse a cycle:** the server at the command (`routing_zyklus`) and the core at load (`format`). `routing_grenze` now means only "all 16 groups are used".
- **Agent texts and tools** (`djk/hand/hand.ts`, `AUFRUF.md`) state groups 1..16, group ids as members of `gruppenspur_neu`, the delete rule, `routing_zyklus` and the refusals of decision 8.
- **Cost.** One pass per level; a flat project has one level. The cost run (`kern_kosten_arr`, "arr32 + 3 levels, 12 groups, one insert per group" against the gate of 1650 us) is task 9; its result is not in this ADR.
- **Listening.** Decisions 1, 2 and 4 are audible and are Andreas' to judge in the acceptance listening.
- **Open.** Insert stages per strip and pool sizes unchanged (decision 5). The page work (task 7) is on its own branch.
